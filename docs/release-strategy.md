# Release Strategy

## Overview

`openclaw-desktop` uses trunk-based development with Semantic Versioning and Git tag driven releases.

Goals:
- keep `main` releasable
- publish reproducible release artifacts from immutable tags
- validate release packaging before merge
- maintain version consistency across frontend and Tauri metadata

## Versioning

The project uses SemVer: `MAJOR.MINOR.PATCH`.

- Patch: bug fixes, stability improvements, small UX fixes
- Minor: backward-compatible features and meaningful product improvements
- Major: breaking changes, incompatible configuration changes, or major UX shifts

Pre-releases are supported using tags such as:
- `v0.3.0-beta.1`
- `v0.3.0-rc.1`

## Branching

- `main` is the source of truth
- all changes land through pull requests
- short-lived branches only
- releases are created from tags, not long-lived release branches

## CI Requirements

All pull requests to `main` must pass:
- frontend lint
- frontend typecheck
- frontend tests
- frontend production build
- Rust check
- Rust clippy
- Rust tests
- Linux Tauri smoke release build
- version consistency check

## Release Process

1. Merge releasable changes into `main`
2. Open a small PR that bumps the version consistently in:
   - `package.json`
   - `src-tauri/tauri.conf.json`
   - `src-tauri/Cargo.toml`
3. Merge the version bump PR
4. Create a tag like `v0.2.1`
5. GitHub Actions builds release artifacts and publishes a GitHub Release
6. Validate assets and release notes

## Release Channels

### Stable
- triggered by tags like `v0.2.1`
- publishes a GitHub Release

### Beta / RC
- triggered by tags like `v0.3.0-beta.1`
- publishes a prerelease on GitHub

### Canary
- optional future workflow
- builds artifacts from `main` without publishing an official release

## Artifacts

The release workflow publishes:
- Linux bundles generated by Tauri
- checksum manifest (`SHA256SUMS.txt`)
- GitHub Release notes

The initial implementation targets Linux only. macOS and Windows can be added later once signing and packaging are ready.

## Rollback

If a release is defective:
- do not replace artifacts under the same tag
- fix forward on `main`
- publish a new patch release

## Notes

- Tags are the only release trigger
- Version metadata must stay in sync across package and Tauri files
- Release automation should publish only what CI has already validated
